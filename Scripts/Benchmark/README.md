# Release benchmark harness

Compile `Consumer.swift` in two separate executable packages: one linked to pinned JLSwift `15aa75164145414f3d5ffb801401c52d40cc5bcc` with the `PREDECESSOR` compilation condition, and one linked only to SwiftJLS without that condition. Use tools 6.2 or newer, Swift 6 language mode, and `swift build -c release`. These development consumers are outside the shipped library graph.

Run `compare.py --predecessor /path/to/old/Benchmark --successor /path/to/new/Benchmark --output /path/to/results` from SwiftJLS. It uses four alternating process blocks per case, each with five warm-ups and five measured iterations, and retains all raw timings. Full sample validation precedes timing. This compares supported public APIs with owned decode, including required admission/validation work. Fixture sizes include odd non-square, 512², 2048² and 4096×3073, at 12 and 16 meaningful bits with flat/ramp/seeded-noise samples.

RSS is the whole-process high-water mark and includes caller input storage and runtime overhead. It is not pixel-allocation or copy instrumentation; unavailable counters are explicitly null. Developer-workstation runs are advisory unless power, thermal state and competing load have actually been controlled. Investigate latency/memory regressions and encoded-size changes under PERF-03; do not silently convert a benchmark failure into a pass.

`verify-exports.py` is a separate correctness experiment for the large-noise cases whose predecessor/successor codestreams differ. Compile the same consumer source, then pass `--predecessor`, `--successor`, `--oracle` (the pinned mapping-capable CharLS driver) and `--report`. It exports one stream per producer, checks every independently decoded sample and cross-decodes both directions. `SWIFTJLS_BENCHMARK_EXPORT` and `SWIFTJLS_BENCHMARK_DECODE` are only for this untimed experiment; leave both unset for performance measurements.

The runner also retains binary SHA-256 values, power-source and load-average snapshots at the beginning and end. These observations improve reproducibility; they do not establish controlled hardware. A battery-powered run remains advisory even when no thermal warning is reported.

Interpret encode timing as public-API operation cost, not isolated kernel cost. The pinned predecessor validates sample ranges in `MultiComponentImageData` construction before timing; SwiftJLS validates them during encoding (full-width ranges need no scan). Source preparation is outside timing for both APIs. A controlled end-to-end comparison must additionally time those preparation boundaries; do not attribute all observed differences to codec kernels or silently waive them.

Use `--end-to-end` to retain two additional distributions: `prepare_seconds` measures public input construction, and `prepare_encode_seconds` measures construction plus encoding together. Both producers start from the same canonical planar UInt16 samples, generated outside timing. Preparation includes layout conversion, allocation, descriptor construction and the predecessor's input validation; the successor's meaningful-bit validation remains in encode. Combined observations are measured directly, not calculated by adding medians. Input destruction is outside timing. The canonical samples and reusable source remain live, so RSS includes those buffers and is not a per-operation workspace figure. Rebuild both consumers from the same current `Consumer.swift` before using this option.

```sh
# Run only in the controlled hardware window for performance evidence.
python3 Scripts/Benchmark/compare.py --predecessor OLD --successor NEW --output NEW_SCALAR_DIRECTORY --end-to-end
python3 Scripts/Benchmark/compare.py --predecessor OLD --successor NEW --output NEW_COLOUR_DIRECTORY --colour --end-to-end
```

Adding `--smoke` validates the measurement harness on small images. The dedicated `Benchmark measurement smoke` workflow does this for both scalar and colour profiles using the pinned predecessor; its timings are not release performance evidence. Every generated summary explicitly starts with `performance_qualified: false`: a human-reviewed qualification record must establish controlled conditions and disposition of regressions. No runner flag waives PERF-01..03.

`python3 Scripts/Benchmark/test-runner.py` checks rejection of nonzero consumer exits, old timing schemas, missing/nonfinite samples, mismatched profiles, impossible timing boundaries, inherited export/decode environment variables and reuse of an existing evidence directory. Missing host-specific power/thermal tools are recorded as unavailable, so Linux smoke tests can run without claiming power control. Old evidence directories are never overwritten.

Use `compare.py --colour` with the same binary arguments for RGB at NEAR 0/3 and all three interleaves. The extended consumer takes optional trailing `COMPONENTS NEAR INTERLEAVE` arguments; the original scalar invocation is preserved. Colour output is checked against each channel's expected samples before timing. SwiftJLS includes RGB interpretation metadata where required; encoded-size differences include that signalling and must be investigated per profile. `--smoke` restricts the corpus to 37×23 for harness/correctness validation and is explicitly not a performance gate. Full colour mode contains 144 cases; plan a controlled window accordingly. The JSON environment retains consumer/runner source hashes as well as binary hashes.

For a targeted repeat or a bounded representative run, use `--cases cases.json`. The file is a nonempty array of seven-field arrays: `[width, height, bits, pattern, components, near, interleave]`, for example `[[2048, 2048, 16, "noise", 3, 0, 0]]` with `--colour`. Every case must belong to the standard grid selected by `--colour`/`--smoke`; duplicates, malformed fields and out-of-grid cases are rejected before writing evidence. The environment records the exact case list and selection-file hash. Selected cases retain all four paired blocks and twenty measured observations per producer/operation. Selection changes coverage, not the performance threshold; never describe a subset as the full grid. Use a new output directory for each repeat.

The current development consumer explicitly configures SwiftJLS with a 1 GiB workspace ceiling and 2 GiB overall memory ceiling so the conservative admission estimate for 4096×3073 RGB fixtures can fit. Other limits retain their defaults. Production `ResourceLimits` defaults are unchanged; the pinned predecessor has no corresponding admission API. Every raw record identifies this as `successor-workspace-1GiB-memory-2GiB-v1`, and the runner rejects older consumer records without that profile. Rebuild both consumers after this change. Earlier default-limit runs retain their original scope; a rejected large fixture is a resource-admission failure, not a latency observation. The public workspace counter remains unknown.
