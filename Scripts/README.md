# Headless Swift 6.4 validation

For current native-codec checks, use `swift test`, `swift test -c release`, separate address/thread sanitizer runs, the independent consumer and CLI scripts described in [current validation](../Documentation/Engineering/CodecMigration/Validation.md). [The completion audit](../Documentation/Engineering/CodecMigration/Completion.md) records their exact revision scope and remaining gates. On the tested Command Line Tools host, Swift Testing requires the explicit bundled macro-plugin flag recorded there.

## Reusable compiler and native-codec runner

The runner originated at the compiler-upgrade checkpoint and now exercises the maintained native-codec consumer. Archived runners and qualification evidence remain unchanged. A successful selected check establishes only its recorded source, toolchain and execution scope.

`validate.sh` invokes the Python 3 standard-library runner on macOS. Run it from any directory; it finds this repository from its own location. It selects Xcode through `DEVELOPER_DIR`, never changes `xcode-select`, and accepts **Apple Swift 6.2 or 6.4**, recording the exact compiler and Xcode identities. Swift 6.4 remains the primary qualification toolchain. Linux checks run separately in CI.

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer ./Scripts/validate.sh
```

The default run checks debug and release clean/incremental builds and tests, a fresh standalone local consumer, five fixed repetitions of selected ownership/cancellation tests, and build-associated SPDX/CycloneDX SBOM generation. It always requests **`--build-system swiftbuild`**; there is no automatic fallback to deprecated engines. Each run gets a new evidence directory and isolated build/cache paths. Build concurrency defaults to two workers per command; use `--jobs` (1–32) deliberately when running several repositories in parallel.

The consumer compiles the checked-in [independent example](../Examples/IndependentConsumer/Sources/Consumer/main.swift) unchanged with a tools 6.2 manifest, Swift 6 language mode and macOS 26.0 deployment floor. It verifies native lossless coding, every logical padded 12-bit sample, destination allocation identity and operation copy/allocation reports. The generated manifest names its local dependency explicitly, so differently named checkouts and worktrees are supported. Its source and manifest hashes are recorded. This local-path check does not establish URL or semantic-version resolution, physical-device behaviour or independent allocator telemetry.

```sh
# Add separate AddressSanitizer and ThreadSanitizer builds/runs.
./Scripts/validate.sh --sanitizers

# Select a bounded subset; this does not qualify omitted checks.
./Scripts/validate.sh --checks debug,repetition --repetitions 10

# Exercise the maintained native consumer in a fresh build directory.
./Scripts/validate.sh --checks consumer --output /absolute/new/consumer-evidence

# In a host sandbox that refuses SwiftPM's nested sandbox only:
./Scripts/validate.sh --disable-package-sandbox --output /absolute/new/evidence-directory
```

`--disable-package-sandbox` is an explicit workaround for `sandbox-exec: sandbox_apply: Operation not permitted`; it disables only the nested SwiftPM sandbox. It does not weaken concurrency, compiler safety checks or the outer host sandbox. Leave it off on an ordinary supported runner.

`report.json` records exact argument arrays, command exit codes, logs, source hashes, toolchain identity, selected/omitted checks, discovery and execution counts, and open gates. A command failure, timeout, zero discovered/selected/executed tests, a discovered/executed declaration mismatch, or a skipped test ends the run unsuccessfully. The script retains all failure evidence. It never uses `--repeat-until pass` or retries a failing test until green.

Swift Testing's xUnit output counts test declarations, including a parameterised test as one declaration. The report separately counts passing argument cases and their fixed repetitions from the raw test log; logs remain authoritative. The runner enables XCTest too if it discovers XCTest imports/subclasses in the source, so it cannot silently hide new XCTest cases. A sandbox bundle-loading failure is a failed environment gate, not zero passing XCTest tests.

SBOMs are generated by `swift build --product <this-package> --sbom-spec spdx|cyclonedx`, using the exact candidate graph and build invocation. Their SHA-256 values are recorded. If the installed tool reports missing validation schemas, that warning becomes an explicit open gate; JSON parsing alone is not schema validation. The separate `swift package generate-sbom` command is graph-only and must not be substituted as build-associated evidence. SwiftPM's SBOM does not inventory every toolchain/platform or non-SwiftPM component.

This script covers the selected local macOS native-codec checks. Native Linux/Intel or device execution, comparison across toolchains, fresh URL consumer resolution, Xcode GUI/front-end qualification, performance measurements and release approval require separate evidence. Compiler CLI help and supported values are captured in every successful run; no unverified hosted CI image is assumed.

## Current OS 26 CLI checks

Active packages and generated consumers require Apple OS 26.0. The owner-approved CLI foundation is a separate executable product, with no main entry point in library tests. After building its release binary, run `python3 Scripts/test-cli.py --binary /absolute/path/to/the/tool --output /new/evidence/directory` for process-level help/verbosity/stream and staged install/man-page checks. The check requires `man` and `mandoc`; missing manual tools fail explicitly. `install-cli.sh --help` describes install/update and DESTDIR staging. Read [CLI.md](../CLI.md) and [current evidence](../Documentation/Engineering/CodecMigration/Validation.md).

The migration follow-up also runs [bounded concurrent resources](../Examples/ResourceStress/README.md) and [Heaptrack peak replay](StorageEvidence/README.md). These ordinary-build measurements remain separate from sanitizer RSS and from controlled release timing.

The [release benchmark harness](Benchmark/README.md) includes scalar and RGB NEAR 0/3 modes, all colour interleaves, source/binary hashes and explicit smoke checks. Controlled scalar/colour timing remains a release gate.
