# Candidate005 memory disposition — publication draft

Candidate005 closes the identified parser-admission and restart-directory growth gaps and completes the source-level algorithm-storage inventory with fresh scoped heap/copy evidence. This is a memory-accounting disposition, not a declaration that milestone4 or stable-release qualification is complete. The current RSS comparison still needs its independent PERF-03 disposition; physical-device testing remains pending and milestone5 is deferred.

Every parser admission now includes the existing 64 KiB control allowance, including metadata-free inspection. Restart directories reserve capacity once after checked memory admission and an encoded-length prerequisite: each nonempty entropy range requires at least one entropy byte and two following marker bytes. A tiny truncated stream therefore cannot trigger a large reservation based only on declared height. Four new tests cover exact workspace/aggregate limits, metadata charging before allocation, valid restart counts around powers of two, and rejection before a destination lease is consumed. All 157 host tests passed in debug, release, Address Sanitizer and Thread Sanitizer against the receipt-bound candidate005 source.

The gradient lookup tables now store signed Int8 values and widen on lookup. Actual table payload is `2*T3+1` bytes, while admission deliberately retains the previous conservative two-Int-table allowance. The inventory states each operation's context, row, scheduling, descriptor, metadata, directory and compressed-buffer storage and lifetime. It also preserves the fact that bounded algorithm workspace can exceed a small final frame: the maximum-table scalar NEAR source payload is 143,779 bytes for a 66,306-byte sample image on 64-bit Int.

Fresh ordinary-release Linux ARM64 evidence covers all 89 established profiles. Every raw allocation profile replayed with the unchanged corrected classifier, all 267 profile commands passed, all sample checks passed, and no codec allocation or live codec baseline byte remained unattributed. The 23 owned decodes each created one final pixel allocation; the other 66 operations created none. The 20 copy controls passed: ten normal zero-source-copy cases and ten positive controls observing exactly the retained source capacity. This instrumentation does not observe inlined copies; code/owner/allocation checks remain part of the proof.

The maximum-table scalar NEAR encode recorded 143,891 requested algorithm heap bytes above a 48-byte baseline, reducing its peak by 917,497 bytes versus candidate004, exactly matching the table payload reduction. Restart inspection removed 18 metadata/control allocation calls and 4,608 cumulative requested bytes; its metadata/control live peak was 1,008 bytes lower. The largest simultaneous whole-operation requested-heap peak in the measured matrix was 6,283,207 bytes, including a 3,969,192-byte live baseline. Category peaks are never added together.

This satisfies the bounded-storage and scoped-accounting interpretation of MEM-10, supported by MEM-12/API-07's explicit treatment of unknown measurements. Logical admission allowances, observed requested heap, and process residency are different quantities. Compiler stack placement, runtime allocations, allocator usable-size overhead and a universal all-input/concurrent total remain unknown. Production `peakWorkspaceBytes` stays `nil`; the existing empirical `pure_algorithm_workspace_complete` flag stays false because that flag denotes a combined pure stack/heap quantity the tooling does not measure. Neither is replaced with the conservative reservation or a sampled maximum.

No additional algorithm-admission or scoped heap-attribution defect was found in this review. Remaining RSS/performance conclusions require their own frozen experiments; target-platform and physical-device status must continue to be reported independently. Historical archives and their original incomplete-status statements remain immutable. New records identify candidate005 by its exact source receipt and source-file hashes rather than relabelling candidate004 measurements.
