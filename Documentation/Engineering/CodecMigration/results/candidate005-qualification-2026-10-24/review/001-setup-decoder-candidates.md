## 1. Replace only destination bookkeeping with monotonic atomic state

Image.swift:129–134 uses a Mutex for started, finished and admittedOwnedStorage. The last is immutable after construction. On success, write takes that mutex to claim its single-use flag at 196–200, takes it again to mark completion at 222, and deinit takes it once more at 165. None of those critical sections borrows pixels or calls a provider.

A private Atomic<UInt8> state ready/inProgress/finished plus an immutable owned-admission Bool can represent exactly these transitions. Compare-exchange ready→inProgress only after the existing metadata and combined-memory checks. Use the same already-used error on any failed claim. Store finished only after successful validation/final cancellation, or after successful abort. If abort fails, leave inProgress so deinit retries. Deinit loads the state and aborts unless finished. Acquire/release ordering (or stronger) is sufficient; no unchecked Sendable or public API change is required.

Keep OwnedImageStorage's separate operationActive CAS, mutex, UUID lease and borrow/seal operations unchanged. Keep all pre/post-fill and final cancellation calls, the public/provider validation path, metadata-before-claim retry ordering, capacity checks and final immutable owner. This does not merge the pixel critical sections or replace a public lease token. It removes three destination mutex lock/unlock pairs from successful preparation; an actual speedup is unmeasured.

Existing DestinationLifecycleTests covers no-abort-on-success, abandonment, failed-fill cleanup, abort retry, failed sealed validation and cancellation during seal. OwnedAdmissionTests covers metadata rejection/retry and public allocated-storage lease behaviour. Add a real concurrent same-destination write race: exactly one body executes and seals, losing callers receive the exact already-used error, the returned image retains correct samples, and release adds no abort. Existing concurrent storage-reservation tests exercise a different gate and are not sufficient alone. Reentrant write should likewise reject without executing its nested body.

## 2. Narrow gradient-table payload from Int to Int8

JPEGLSRegularMode.swift:49 and JPEGLSRegularModeDecoder.swift:46 declare private [Int] tables. Every interval fill and fallback value is in -4...4; the encoder's stored interior values are in -3...3. Both quantizeGradient methods return Int, and their callers use only that result. Use [Int8], retain Int counts/offset/index arithmetic and outer clamps, and widen the selected element with Int(...). The decoder reference fallback result can be converted exactly with Int8(...); do not use truncation or merge the different encoder/decoder fallback precedence.

The maximum 2*T3+1 payload has 131,071 elements: on 64-bit this changes 1,048,568 to131,071 bytes. At default 12/16-bit NEAR 0, T3=276 gives 553 elements: 4,424 to553 bytes. This reduces initialized bytes and cache footprint without a global cache or retained extra allocation. It applies to both encoder and decoder and all callers of their quantizers, including scalar/interleaved paths. It does not change QualifiedMonochromeDecoder, which uses its own branch quantizer.

Preserve the existing conservative Int-based ScalarCodec.tableBytes admission initially. Narrowing that admission at the same time would change public resource-limit acceptance, independently of the representation optimisation. Update current payload accounting only after measurement; historical Int payload receipts remain historical. The constructor-name-based algorithm-state classifier is compatible in principle, but actual new stacks/sizes must still be reconciled.

GradientTableTests already independently checks 120 small ordered threshold triples and all 9 NEAR values; defaults 2…16 across every possible sample gradient; maximum table extent, equal thresholds, fallback branches, invalid NEAR and Int.min/max outer clamps. These tests specifically catch sign-widening mistakes and preserve the independent expected values. Reuse them plus public lossless/NEAR component fixtures and exact encoded-byte checks. Signed-byte loads may lower directly to sign-extending loads, but emitted hot-loop code and a controlled candidate comparison must verify that narrowing does not add a per-lookup conversion branch or regress throughput. Smaller requested payload is certain; latency benefit is not.
